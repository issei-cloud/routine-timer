# 要件定義書：トレーニング&ストレッチ ルーティンタイマー（仮）

最終更新：2026-11-21 ／ 版：v1.0（構想確定版）

---

## 1. 目的とコンセプト

自宅でのトレーニングとストレッチを**習慣化する**ためのルーティン実行タイマーアプリ。

ユーザーが自分で種目を組み合わせてルーティンを作り、それを順番に実行する。単なるタイマーではなく、「**続けられること**」を最優先に据える。そのため、できなかった日にユーザーを責めない設計思想を全体で一貫させる。

### 設計思想（全判断の基準）

> **ユーザーを責めない。続けやすさを最優先する。**

この原則が、機能の採否・言葉づかい・配色・記録方法のすべての判断基準になる。迷ったときはこの原則に立ち返る。

---

## 2. ターゲットユーザーと利用シーン

- **主ユーザー**：自宅で運動・ストレッチを習慣にしたいが、「次に何をするか迷う」「続かない」「できない日に落ち込む」ことが壁になっている人。まず開発者自身。
- **利用シーン**：朝の目覚めのストレッチ、夜の就寝前のリラックス、日中の運動習慣など。時間帯や目的の異なる複数のルーティンを使い分ける。
- **位置づけ**：開発者の個人利用が出発点。使い勝手が良ければ公開も視野。ポートフォリオ作品としても用いる。

---

## 3. 機能一覧（優先度別）

### MVP（初版・必須）
| 機能 | 内容 |
|---|---|
| ルーティン実行 | 種目を順に進行。時間種目は自動、回数種目は手動完了 |
| 休憩の自動挿入 | 各種目の後ろに設定秒数の休憩を挟む |
| 進捗表示 | 進捗バーで全体の残量を可視化 |
| 動作確認画像 | 種目ごとに静止画を複数枚表示・切り替え |
| シンプル記録 | 実行後に「しっかり/少し」の2択で記録 |
| カレンダー振り返り | 日ごとの状態を色で表示。休息日も否定的に見せない |
| 複数ルーティン選択 | ホームから登録済みルーティンをワンタップで選び開始 |

### 第2段階
| 機能 | 内容 |
|---|---|
| 音声 | 区切りの通知音・ヒーリングBGM（各オンオフ可） |
| ルーティン編集 | 種目の追加・削除・並べ替え・時間や休憩の変更をGUIで |
| 画像登録 | ユーザーが撮影画像やフリー素材を種目に登録 |

### 将来的な拡張
- 連続記録のゆるやかな可視化（※あくまで「責めない」範囲で）
- 種目プリセットライブラリ（他ユーザー向け公開時）
- 複数端末同期 / バックアップ

## 4. 各機能の詳細仕様

### 4.1 ルーティン
- 「種目を好きな順に並べた1セッション」。
- 朝・夜など複数登録でき、ホームから**ワンタップで選んで即開始**。都度の選択に手間をかけない。

### 4.2 種目（エクササイズ）
各種目が持つ情報：
- **名前**
- **進行タイプ**：時間ベース／回数ベース。**1ルーティン内に混在可**（ストレッチは時間、筋トレは回数になりやすい）。
- **時間（秒）または回数**
- **後ろの休憩秒数**：休憩は独立した項目として一覧に並べない。*理由：一覧の視覚情報が増えすぎるのを避ける。*
- **動作確認用の静止画（複数枚）**：開始姿勢→終了姿勢のように動きを示す。*動画・GIFは管理コストが高いため不採用。*

### 4.3 実行画面
- ルーティンを頭から順に進行。
- 時間種目：カウントダウンし0で自動的に次へ。
- 回数種目：ユーザーが「できた」を押して手動で次へ。
- 種目の後に休憩秒数を自動挿入。
- 静止画を表示、複数枚は切り替え可。
- **進捗バー**で全体のどこまで進んだかを可視化。*残量が見えることが安心感につながる。*
- スキップ・中断が可能。

### 4.4 音声（第2段階）
- **区切りの通知音**：種目や休憩の終わりに鳴らす。*目を閉じていても区切りが分かる。*
- **ヒーリングBGM**：実行中に流す。*別アプリで音楽を流す手間を省く。*
- 上記は**個別にオンオフ可**。

### 4.5 記録
- 実行後に**「しっかりできた」「少しできた」の2択**。時間・回数は入力させない。*入力の手間が習慣化を妨げる。*
- **「休息の日」は選ばせない**。アプリを開かなかった日が自動で「休息の日」になる。
- できなかった日を責める表現・演出を一切しない。「失敗」ではなく「休息」。

### 4.6 振り返り
- **カレンダー形式**で、日ごとの状態を色分けした印で表示。
- 休息日も否定的に見えない配色（赤・警告色を使わない）。

## 5. 画面一覧と遷移

| 画面 | 役割 |
|---|---|
| ホーム | 登録ルーティンの一覧。選んで開始。記録画面への入口 |
| 実行画面 | 種目・休憩を順に進行。進捗バー・画像・タイマー |
| 完了画面 | 「しっかり/少し」の2択で記録 |
| カレンダー | 日ごとの状態を色で振り返る |
| 編集画面（第2段階） | 種目・ルーティンの作成と編集 |

```
ホーム ──選択→ 実行画面 ──完了→ 完了画面 ──記録→ カレンダー ──→ ホーム
  └──────────────────────→ カレンダー（記録を見る）
  └──→ 編集画面（第2段階）
```

## 6. データ構造

```
Routine（ルーティン）
  - id
  - name            … "朝のリセット" など
  - items[]         … Exercise の並び（順序が意味を持つ）

Exercise（種目）
  - id
  - name
  - mode            … "time" | "reps"
  - value           … 秒数（time）または回数（reps）
  - rest            … 後ろの休憩秒数（0可）
  - images[]        … 静止画の参照（複数）

Log（記録）
  - date            … "YYYY-MM-DD"（1日1件）
  - status          … "full" | "some"
                      ※ 記録のない過去日は "休息の日" として扱う（保存はしない）

Setting（設定）
  - chimeOn         … 区切りの音 on/off
  - bgmOn           … BGM on/off
```

*補足：記録は1日1レコードで十分。「休息」をデータとして持たず「レコードがない状態」で表現するのが、責めない設計をデータ構造レベルで体現している点。*

## 7. 非機能要件

- **オフライン動作**：自宅・通信環境を問わず使うため、ネット接続なしで完結することが望ましい。
- **起動と操作の軽さ**：習慣化アプリは「開くまでの手数」が命。起動が速く、2タップ以内で実行開始できる。
- **対応端末**：スマートフォン縦画面を主対象。片手操作を想定。
- **データ永続化**：アプリを閉じても記録・ルーティンが残る。
- **音声**：ブラウザ実装の場合、初回操作まで音が出ない制約（自動再生ポリシー）を考慮。

## 8. 技術スタックの提案（要検討・開発者が選択）

個人開発・ポートフォリオ・オフライン重視を踏まえた候補。

| 選択肢 | 長所 | 短所 | 向く人 |
|---|---|---|---|
| **PWA（React等のWeb + オフライン対応）** | 1つのコードで全端末。URLで公開でき**ポートフォリオに最適**。学習範囲が集中 | ネイティブほどの細かい制御は不可 | **本件の第一推奨** |
| ネイティブ（React Native / Flutter） | 端末機能をフルに使える。ストア配布 | 環境構築・審査の手間。学習コスト大 | ストア公開を強く望む場合 |
| Web（オフライン非対応） | 最も手軽 | オフライン不可・保存が弱い | 試作のみ |

**推奨：PWA**。理由は、(1) オフライン動作という非機能要件を満たせる、(2) URLひとつで見せられてポートフォリオと相性が良い、(3) 1コードベースで完結し個人開発で完遂しやすい、(4) 後からストア配布への発展余地も残る。

データ保存は、MVPでは**ブラウザのローカル保存（localStorage / IndexedDB）**で十分。サーバーやDBは複数端末同期が欲しくなった段階で検討。画像も同様にMVPはローカル保存から始め、公開時に外部ストレージを検討。

## 9. 開発の進め方（マイルストーン）

1. **M1：土台** … 型定義（Routine/Exercise/Log）、ローカル保存の仕組み、画面遷移の骨組み
2. **M2：実行画面** … アプリの核。タイマー・休憩自動挿入・進捗バー・画像表示。*ここの触り心地が全て。最優先で仕上げる。*
3. **M3：記録とカレンダー** … 2択記録、休息日の自動表現、カレンダー可視化
4. **M4：ルーティン選択とホーム** … 複数ルーティンのワンタップ選択
5. **M5：音声** … 通知音・BGMとオンオフ
6. **M6：編集画面** … 種目・ルーティンのGUI編集（それまではデータ直書きで運用可）

*M2まででアプリの価値の大半が体験できる。M6（編集）は後回しでよく、初期はコード内のデータを直接編集して回せる。*

---

## 10. リスクと検討課題

- **設計思想の揺らぎ**：AI補助で開発すると「連続達成が途切れました」等の“責める”機能が無意識に混入しやすい。ルールとして明文化し歯止めをかける。
- **画像管理のコスト**：種目ごとの静止画を自分で用意する負担。MVPはプレースホルダや最小枚数で始める。
- **音声の制約**：ブラウザの自動再生ポリシー。初回タップ後に鳴る設計で回避。
- **スコープの肥大**：編集機能や同期を早く入れたくなるが、M2（実行体験）の完成を優先する。

---

## 付録：ポートフォリオとしての見どころ

- **設計思想を貫いた一貫性**：「責めない」をデータ構造（休息を"記録なし"で表す）まで落とし込んでいる点は、設計を語れる題材になる。
- **時間/回数の混在進行**と**休憩の自動挿入**という状態遷移の設計。
- **オフライン動作するPWA**としての実装。
